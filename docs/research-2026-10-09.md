# 외부 사례에서 Gooo로 가져온 것 — 2026-10-09

Hacker News와 GeekNews의 당일 글, GitHub의 일간 Trending을 살펴보고
원문 문서와 구현 저장소로 따라갔습니다. 현재 작업과 맞는 작은 연결부터 적용합니다.
인기 순위와 별 수는 사례를 찾는 데만 사용했습니다.

## 상태를 주고, 선택을 남기고, 다시 실행하기

Hacker News에서 본 [Jevman](https://news.ycombinator.com/item?id=50007993)은
팩맨의 갈림길마다 현재 상태와 가능한 방향을 모델에 주고 게임을 기록합니다.
원문은 시간 제한 후 보조 규칙을 쓴 횟수, 지연, 점수와 재생을 함께 다룹니다.
[프로젝트 설명](https://opper.ai/jevman-benchmark/)과
[확인한 구현 시점](https://github.com/opper-ai/jevman-benchmark/tree/1c8b77ac61bafa10956c601b1c9b339dcd277836)을 참고했습니다.

Gooo에는 이미 제한된 조립 선택, 작성된 사례 검사, 선택한 프로그램의 저장 재생이
있습니다. 이 사례를 보고 다음 실험의 단위를 더 분명히 잡았습니다. 하나의 결정에는
입력 상태, 선택한 프로그램, 관측 결과, 재생 기록이 함께 있어야 합니다.
모델이 반환한 확률을 기능의 완성률로 읽으면 안 됩니다. 조립 과정의 검사와 별도
입력에서 실행한 결과를 각각 측정합니다. 모델 지연 시 처리도 기록할 다음 실험입니다.

## 짧은 진단에서 원본까지 찾아가기 — 이번에 적용

GitHub Trending에서 본 [claude-mem](https://github.com/thedotmack/claude-mem)은
작은 색인을 먼저 보고 필요한 관측을 더 읽는 구조를 설명합니다.
[원문 설계 설명](https://docs.claude-mem.ai/progressive-disclosure)과
[확인한 저장소 시점](https://github.com/thedotmack/claude-mem/tree/fa8ab09f06aa05f958c5225cf3756ce52a3ebb96)을 참고했습니다.

이 원리를 `diagnose`의 프로세스 실패 경로에 적용했습니다.
`next-context.json`은 타입이 있는 상태와 Gooo가 만든 작업을 보여줍니다.
긴 출력과 원래 오류는 근거 파일에 남고, 요약에는 파일 경로·지문·바이트 수·JSON
위치가 있습니다. 비유하면 진료 기록 전체를 매번 펼치는 대신, 현재 소견에서 당시
검사 기록을 바로 찾는 방식입니다. 연결 부분은 Go이며 별도 서비스나 새 모델은
추가하지 않았습니다. 생성된 context를 다음 모델 호출에 자동 투입하는 루프는
후속 작업입니다.

## 실패 기록을 실행 가능한 규칙으로 바꾸기

GeekNews의 [6월 논문 모음](https://news.hada.io/topic?id=30531)에서 찾은
[Self-Harness](https://arxiv.org/abs/2606.09498v3)는 실행 흔적에서 약점을 찾고,
작은 운영 정책 변경을 제안하고, 회귀 검사로 확인하는 과정을 제시합니다.
논문은 6월 8일 제출, 확인한 v3는 8월 20일 수정본입니다. 10월 새 논문으로
분류하지 않았습니다. [저자 저장소](https://github.com/qzzqzzb/Self-Harness)도 확인했습니다.

진행 중이던 Gooo 작업은 실제 Windows 실패를 읽어 `process-next.gooo`의 분기로
다음 작업을 만드는 데까지 와 있었습니다. 이번 조사는 이미 만든 기능을 대조하고
다음 실험을 정하는 데 사용했습니다. 실패가 새로 생길 때 원본 기록과 회귀 사례를
함께 추가하고, 변경된 Gooo 규칙을 저장 프로그램으로 다시 실행해 보는 방향입니다.
현재 작은 모델의 학습 규모와 평가 범위에서 논문의 성과를 기대할 근거는 아직 없습니다.

## 처음 검토한 두 가지

- HN의 [OSC 7501 제안, 10월 6일](https://mitchellh.com/writing/program-status-osc7501):
  프로그램이 상태를 직접 알리는 방식입니다. 현재 Gooo의 구조화된 실행 상태를
  터미널에 표시하는 연결을 검토할 수 있습니다. 이번 변경에는 프로토콜 구현이 없습니다.
- GeekNews에서 본 [tinyjsapp](https://github.com/tarwin/tinyjsapp): 실행 환경의
  `capabilities()`와 `requirements()`를 조회해 사용할 기능을 고릅니다.
  Gooo도 패키지의 선언 정보와 실행 환경에서 확인한 기능을 이어 주면,
  생성 가능한 경로를 사용 전에 설명하는 데 도움이 될 것으로 봅니다. 이후 아래의 사전 확인과 조립 연결에 적용했습니다.

## 사용 흐름에 적용한 것과 보류한 것

후속 구현으로 `assemble`을 추가했습니다. 컴파일러의 `body-context --model`로 실제
소스와 모델을 확인하고, `assembly-route.gooo`가 모델·고정 순서·중단 중 다음 경로를
선택합니다. 조립과 원본 저장, 같은 프로그램의 재실행까지 한 명령으로 이어집니다.
[실행 예제](../examples/model-assembly/README.md)에 바로 쓸 명령과 결과 파일을 설명했습니다.

| 살펴본 원리 | 이번 결정 | 이유와 적용 범위 |
| --- | --- | --- |
| tinyjs의 기능·필요 조건 조회 | 적용 | 소스 입력을 읽을 수 있는지 먼저 확인하고, 모델의 표현 범위 밖이면 선언된 순서로 진행 |
| claude-mem의 색인에서 원본으로 내려가기 | 적용 | 짧은 보고서에서 긴 입력 그래프를 빼고 원본 파일·입력 지문을 연결 |
| 개발 글에서 독자의 다음 행동부터 설명하기 | 적용 | 첫 명령, 선택 이유, 결과 위치를 먼저 보여주는 예제와 터미널 출력 |
| OpenTelemetry의 도구 간 관측 공유 | 보류 | 원본 JSON과 소스 지문은 계속 공개하되 OTLP 연결은 실제 소비 도구가 생길 때 추가 |
| OSC 7501의 터미널 상태 전달 | 보류 | 상태 문구와 종료 결과부터 개선; 프로토콜과 터미널별 동작은 별도 확인 필요 |

기존의 수동 모델 경로 판단과 요약에 전체 그래프를 넣는 단계를 줄였습니다.
입력 한계에 대한 거절과 파일·모델 오류는 각각 기록합니다. 경로를 고르는 Gooo 규칙은
정해진 상태를 다루므로 결정론적으로 실행하고, 후보 순서를 제안하는 작은 모델은
대상 본문의 조립에서 사용합니다. 필요한 위치에 추론을 붙이는 기준입니다.

HN에서 다시 올라온 [Carson Gross의 Yes, and](https://htmx.org/essays/yes-and/)는
2026년 2월 27일 글입니다. 복잡성을 다루고 생성된 코드를 읽을 수 있어야 한다는 관점을
참고했습니다. Gooo에서는 소스의 조건식·대입식·안정 ID를 보존하고 어떤 후보가
선택됐는지 생성 코드와 함께 남기는 방향으로 해석했습니다.

GeekNews에서 찾은 [Michael Lynch의 글쓰기 사례, 10월 7일](https://refactoringenglish.com/blog/anti-patterns-software-blogging/)는
독자가 얻을 것을 초반에 보여주고 과도한 격식을 덜어내도록 권합니다. 설명을 길게
따라가기 전에 실행과 결과를 볼 수 있도록 이번 사용 안내를 구성했습니다.

[OpenTelemetry의 10월 8일 원문](https://opentelemetry.io/blog/2026/otel-native-by-design/)은
사용자가 선택한 관측 도구로 맥락을 보존해 내보내는 설계를 설명합니다. Gooo의 원본
기록과 짧은 보고서를 연결하는 기준으로 참고했습니다. 현재 출력은 Gooo JSON이며,
OTLP 호환이나 외부 관측 서비스 연동을 구현한 상태로 표시하지 않습니다.

로컬 실행에서 한글·영문 모델 조립, 모델 생략, 한 선택 소스의 고정 순서 전환을
확인했습니다. 각 실행의 호출 사례는 4/4, 필드는 12/12이고 저장 결과가 같았습니다.
이는 공개된 작은 예제에서의 확인입니다. 큰 프로그램에서의 사용성과 독립적인
모델 일반화 평가에는 새 자료가 필요합니다. 없는 모델과 알 수 없는 상태도 별도 검사합니다.

## 이번 구현을 판단하는 범위

실제 Windows 실패 예제로 만든 두 조립 사례에는 필드 검사 6개가 있습니다.
실제 입력의 정답 점수는 0/0으로 남습니다. 같은 실패에서 만든 회귀 자료이므로
별도 일반화 평가로 세지 않습니다. 테스트는 11개 프로세스 상태 조합에서 고정 순서와
기존 자체 모델의 진단을 대조하고, 저장 재생에 새 모델 호출이 없는지 확인합니다.
context 연결은 큰 정수의 보존, 근거 파일의 지문·크기, 진단과 상태의 일치를 확인합니다.

우선 목표는 Gooo 프로그램이 자기 도구의 실패를 읽고 다음 작업을 다른 도구에
전달하는 데 있습니다. 이후 새 실패 종류와 사용자 입력을 별도 평가 자료로 모아,
어느 조건에서 작업 선택이 도움이 되는지 측정하겠습니다.
